------------------------------------------------------------------
SECTION 2 — NON-FUNCTIONAL REQUIREMENTS
------------------------------------------------------------------
Produce at least 3 Non-Functional requirements in requirements[] with category "Non-Functional" and ids prefixed NFR- (NFR-001, NFR-002, ...).

Non-Functional requirements describe HOW WELL the system must behave — the quality attributes and operational constraints. Cover the relevant subset of these categories (choose those that matter for a system of this type, do not force irrelevant ones):
- Performance & scalability (e.g. "p95 API latency < 300ms at 500 concurrent users", "support 10,000 daily active users with linear horizontal scaling").
- Availability & reliability (e.g. "99.9% monthly uptime", "RTO < 15 min, RPO < 5 min").
- Security (e.g. "all data encrypted at rest with AES-256 and in transit with TLS 1.3", "OWASP Top 10 hardening", "MFA for privileged roles").
- Usability & accessibility (e.g. "WCAG 2.1 AA compliance", "core task completable in < 3 clicks").
- Maintainability & observability (e.g. "structured JSON logging", "distributed tracing", "80% unit test coverage").
- Compliance & data governance (e.g. GDPR, HIPAA, PCI-DSS, SOC 2 — only if relevant to the domain).

Each NFR MUST be MEASURABLE and VERIFIABLE — include the concrete target in nfr_targets and phrase the description with a specific threshold, not "the system should be fast". Provide acceptance_criteria that describe how the target is verified (load test, security scan, audit).
